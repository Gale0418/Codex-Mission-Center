# Mission Center Skill 統合設計

## 目標

將 Mission Center 的 repo、個人 Skill、Marketplace 安裝來源與 plugin cache 統一為同一套可靠工作流程。

使用者啟用 Mission Center Skill 後，系統必須能：

1. 持續用一次一題的方式釐清需求，直到完整理解任務全貌。
2. 以跨領域專家 Council 檢查方向、盲點、分歧、風險與驗證方式。
3. 研究本機脈絡、既有方案與網路 Prior Art，避免重複造輪子並遵守授權。
4. 將目標拆成可執行、可驗證且有依賴關係的任務。
5. 將核准後的任務依序發布到 `MissionCenter/tasks.md`，並同步專案摘要、進度與 HUD 狀態。
6. 讓 HUD 以「一個小人代表一個任務」呈現 `tasks.md` 的生命週期。

## 成功條件

- Repo 是唯一可編輯真源，其餘三個位置均由發布流程產生。
- 四份 `SKILL.md` 的 SHA-256 完全相同。
- Skill 不再依 active agent、Owner、程序數或平行工作數量決定 HUD 小人數量。
- 任務研究、拆解、發布、同步及驗證流程有明確輸入、輸出與失敗行為。
- Intake 不因固定題數提早結束，也不為問而問；只有資訊完整才提出任務草案。
- 開放式任務會按需啟動創意跨域 Council，從其他領域遷移原理並收斂成可行的新點子。
- 外部方案經過來源、授權、維護性、安全性與適配度檢查後才能採納。
- `tasks.md`、`project.md`、`progress.md`、`smoke-tests.md` 與 HUD 不會各自維護互相衝突的狀態。
- Skill 與 plugin 驗證、內容一致性檢查及任務生命週期 fixture 測試全部通過。

## 非目標

- 不實作 Codex 與 Antigravity 或其他 AI 程式的跨程序橋接。
- 不重設 HUD 視覺風格或進行無關的前端重構。
- 不修改無關 License、歷史文件或使用者尚未提交的變更。
- 不直接把 plugin cache 當成作者來源或長期手動維護目標。

## 單一真源與發布架構

唯一真源：

```text
D:\MyGame\Codex-Mission-Center\skills\mission-center
```

衍生位置：

```text
C:\Users\USER\.codex\skills\mission-center
C:\Users\USER\.codex\local-marketplaces\mission-center\plugins\mission-center\skills\mission-center
C:\Users\USER\.codex\plugins\cache\mission-center-local\mission-center\<version>\skills\mission-center
```

發布方向固定為：

```text
repo 真源
  -> 個人 Skill 相容鏡像
  -> Marketplace plugin 來源
  -> cachebuster 與插件重裝
  -> plugin cache
```

禁止從任一衍生位置反向覆寫 repo。個人 Skill 保留相容性，但不得成為另一套規格來源。Plugin cache 必須透過正式更新流程刷新，不直接手改。

## Skill 工作流程

### 1. 北極星 Intake

- 若工作區已有 `MissionCenter/`，先讀取 `project.md`、`progress.md`、`tasks.md`、`decisions.md` 與 `smoke-tests.md`。
- 若尚未建立，先完成需求 intake，不得用模糊描述直接生成大量任務。
- 每輪先摘要目前理解、指出一個關鍵缺口、提供精簡意見，最後只問一個最能降低不確定性的問題。
- 持續提問直到目標、使用者價值、成功條件、範圍、非目標、限制、優先級、第一個里程碑、主要風險、依賴與驗證方式均已清楚。
- 初期優先鎖定最終成果與方向；Owner、估時、標籤等管理細節延後處理。
- 資訊完整後提出全貌摘要與任務草案，不再為了形式繼續追問。

### 2. 創意跨域 Council

- 只在開放式產品、體驗、系統或架構問題，使用者要求發明、改善、差異化，現有方案卡住，或跨域遷移可能明顯提升價值時啟動。
- 明確的小型修 bug、機械式同步、格式調整、直接指令及已有唯一正解的例行工作不強制啟動。
- 先從目標抽出核心機制與矛盾，例如氣流、熱、噪音、握持、空間、資訊流或回饋延遲，再尋找其他領域處理相同原理的方法。
- 動態挑選少量最具遷移價值的專家視角，不使用固定企業部門名單。例如吹風機問題可連結熱流工程、工業設計、建築導流、風力機械與仿生原理。
- 發散階段允許類比、反轉、組合、尺度轉換與看似不相干的專業碰撞，不用成本或既有慣例過早淘汰創意。
- 收斂階段再以使用者價值、工程可行性、成本、安全、授權與可驗證性篩選，至少保留一個「意外但做得到」的候選方案。
- 每個入選點子只需說明跨域來源、遷移原理、組合後價值與最小驗證方式，避免冗長角色扮演。
- 預設採混合呈現：一般情況只輸出關鍵靈感、盲點與建議；重大分歧時才展開不同專業立場與取捨。
- Council 是主 Agent 的觀點模擬，不等於自動啟動子 Agent。只有工作可獨立平行、需要獨立驗證且使用者明確同意時，才派遣真正的子 Agent；每批完成後先收回，再決定是否開下一批。

### 3. 研究與 Prior Art Gate

- 搜尋前先簡短記錄原始需求、假設與初步方向，建立獨立形成的脈絡。
- 先研究本機檔案、既有文件與 Git 歷史；資訊具時效性、需要來源、領域陌生或本機資料不足時，再使用網路研究。
- 網路研究優先使用官方文件、標準、論文、原始碼與其他一手來源；一般搜尋受阻時可改用 Jina Reader，Jina Search 僅在已有有效憑證時使用。
- 不得用 Jina 或其他讀取服務繞過登入、授權、付費牆或存取控制；仍無法驗證時明確標註不確定性。
- 搜尋成熟套件、標準、官方範例與相似開源專案，比較「直接採用、包裝整合、局部借鑑、自行開發」。
- 比較授權、維護活躍度、安全性、相容性、成本、退出難度與整合風險；只有現成方案確實不適合時才自行開發。
- 在 `notes.md` 保留簡潔研究紀錄：`搜尋前構想｜參考來源｜採納內容｜授權狀態`。

### 4. Clean-room 與授權政策

- 參考外部方案時只提取需求、概念、原理、公開介面與比較指標，不搬運原始碼、文案、素材或高度獨特的實作結構。
- 需要複製、修改或改作具體內容時，必須先驗證授權、相容性、版本、作者與 attribution 義務。
- 優先考慮 MIT、BSD-2-Clause、BSD-3-Clause、ISC 與 Apache-2.0 等寬鬆授權，但新增依賴或外部服務仍須使用者核准。
- AGPL、SSPL、非商用及授權不明方案預設阻擋；GPL 與自訂授權進入人工審查。
- 無授權的公開專案視為不得複製具體內容，只能在不接觸其表達的前提下參考思想與原理。
- 在 `decisions.md` 記錄候選方案、採用理由、不採用原因與授權判斷。

### 5. 方案與任務定義

- 明確記錄目標、成功條件、限制、非目標、優先級、第一個里程碑、主要風險與驗證策略。
- 提供 2 至 3 種可行方案、取捨與推薦；不可把搜尋結果直接當作未驗證事實。
- 任務必須是可交付的切片；過大或高風險工作先拆成父子任務。
- 使用 Linear 式層級：`Project -> Cycle -> Epic -> Task -> Subtask`，並追蹤優先級、狀態、依賴、下一步與驗證方式。
- 採滾動式規劃：先畫出完整 Epic 地圖，只把第一個可驗證里程碑詳細拆成可執行 Subtask，遠期工作保留較粗的 Backlog。
- 大型或高風險任務走完整流程；小型任務可縮短文件，但不得跳過目標理解與完成驗證。

### 6. 核准與發布任務

- 完全理解任務後先呈現任務樹草案；只有使用者核准後才正式寫入工作區。
- `tasks.md` 是任務順序與生命週期的唯一真源。
- 每個任務至少包含穩定 ID、短標題、類型、父項、優先級、狀態、依賴、下一步與驗證方式。
- 新任務按使用者與依賴順序插入，不得以 active agent 或 Owner 排序。
- 發布後同步 `project.md` 與 `progress.md`；若任務影響 HUD，立即重建視覺狀態。
- 任務未有可重複驗證紀錄前不得標為 `Done`。

### 7. Superpowers 執行閘門

- Linear 管理任務結構、優先級、依賴與狀態；Superpowers 管理頭腦風暴、規格核准、實作計畫、測試、驗證與收尾。
- 流程順序為 `Brainstorm -> Spec -> Plan -> TDD -> Verify -> Closeout`；依風險調整深度，但不得顛倒必要閘門。
- 每個里程碑完成後重新檢查研究、風險與 Backlog，再詳細規劃下一個里程碑。

### 8. 失敗處理

- 缺少關鍵需求時停在 intake，提出一個最能降低不確定性的問題。
- `tasks.md` 格式錯誤時回報可定位的錯誤，不虛構任務或預設小人。
- 同步衍生檔失敗時保留 repo 真源，停止發布並列出失敗位置。
- 不得為了讓 HUD 看起來有內容而生成假任務或主程式佔位角色。

## HUD 生命週期

每一列有效任務對應一個小人，名稱使用任務短標題，順序跟隨 `tasks.md`。

| `tasks.md` 狀態 | HUD 區域 |
|---|---|
| `Backlog`、`Ready` | `Intake` |
| `In Progress` | `In Progress` |
| `Blocked` | `Blocked` |
| `Review` | `Review` |
| `Done` | 休息區 |

顯示規則：

- 主工作區顯示前 10 個未完成任務。
- `Done` 不占前 10 名額。
- 總小人超過 15 時，先淘汰最舊的 `Done`。
- `Blocked` 僅代表真正受阻；smoke test 是完成門檻，不另造衝突狀態。
- HUD 小人數量不得從 active agents、Owner 或程序數推導。

## Skill 文件結構

- `SKILL.md`：保留觸發條件、核心流程、生命週期與必要守則。
- `references/`：保存 HUD、intake、task workspace、驗證與發布細節。
- `scripts/`：保存需要確定性與可重複執行的 bootstrap、seed、sync、validate 與 publish 工具。
- `assets/`：只放實際發布所需的 HUD 資產。

避免在 `SKILL.md` 重複整段範例實作；詳細 schema 與腳本行為放到 reference 或可測試腳本，降低載入成本。

## 工程品質閘門

所有實作都必須同時符合三個核心原則：易於閱讀、易於維護、易於測試。
整體架構同時必須易於更新、易於擴展、易於升級，且不得以預造大量抽象與空目錄假裝具備擴展性。

- 採最小安全變更，只修改完成目前目標所需的區域。
- 避免無關重構，保留既有行為與公開介面；需要改變行為時先寫清楚遷移與相容策略。
- 修改後必須執行可重複驗證；建立但未執行的測試不算完成。
- 模組保持單一責任，依賴方向清楚，介面可理解且可獨立測試。
- 將確實會變動的設定集中管理，避免硬編碼環境路徑、版本與秘密；不為假想需求預造抽象層。
- 擴展新功能應優先新增有邊界的模組或資料映射，不要求修改多個無關元件。
- 升級資料格式、依賴或 plugin 版本時，提供明確版本、相容檢查、遷移步驟與失敗復原方式。

### 反形式主義規則

- 不因為目錄名稱看起來專業就建立空的 `components/`、`services/`、`utils/`、`hooks/` 或其他架構。
- 新目錄、抽象、設定與文件必須服務已確認的需求，並有實際呼叫者或維護用途。
- 測試必須真正執行並記錄結果；失敗、未執行或無法重現時不得標記 `Done`。
- `TODO`、`FIXME` 或暫緩項目必須連結任務 ID，寫明原因、負責人或解除條件；不得建立沒有退出計畫的 `legacy/` 墳場。
- 秘密不得進入版本控制；需要環境設定時提供安全範例與明確驗證，但不提交實際憑證。
- 配額或時間不足時縮小里程碑、保留可重開狀態並誠實標示未完成，不以空檔案、假測試或口頭宣告湊出完成度。

## 更新與防漂移

- 擴充既有 Windows／Unix 安裝工具，從 repo 真源發布完整 Skill 套件。
- 發布前檢查 repo 工作樹，保留目前未提交的 `sync_mission_center.py` 變更。
- Marketplace 來源更新後使用 cachebuster／重新安裝流程刷新 plugin cache。
- 排除 `.git`、`__pycache__`、`*.pyc` 與暫存檔。
- 提供唯讀 dry-run，先列出新增、修改、刪除與雜湊差異。
- 正式發布後再次計算四份 `SKILL.md` 雜湊；不一致視為失敗。

## 驗證策略

### 靜態驗證

- 驗證 `SKILL.md` YAML frontmatter、名稱與 description。
- 驗證 plugin manifest 與 Marketplace metadata。
- 搜尋並拒絕舊的 active-agent roster 規則。
- 檢查 `SKILL.md` 不含互相矛盾的生命週期敘述。

### 行為 fixture

- 模糊大型需求：持續一次問一題，直到 intake 完整才產生任務草案。
- 開放式創意任務：啟動跨域原理遷移，產生至少一個意外但可驗證的候選方案。
- 發散與收斂：創意不被成本過早淘汰，但入選方案通過價值、可行性、安全、授權與驗證檢查。
- 例行小型修正：不強制啟動創意 Council。
- Council 一般情境：只輸出關鍵靈感、盲點與建議，不展開冗長角色台詞。
- Council 重大分歧：呈現相關專業立場、取捨與推薦。
- Prior Art 命中成熟方案：先比較採用與自行開發，不直接建立重造輪子的任務。
- 無授權或高風險授權：阻擋複製與採用，留下簡潔決策紀錄。
- 網路搜尋受阻：依規則降級至 Jina；仍失敗時標示不確定性且不捏造來源。
- 未獲任務樹核准：不得寫入 `tasks.md`。
- 最小安全變更：若 diff 含無關重構或破壞既有行為，驗證失敗。
- 反形式主義：空架構、無使用者的抽象、未執行測試及無任務連結的 `TODO/FIXME` 均不得通過完成閘門。
- 可升級性：資料或 plugin 版本變更缺少相容檢查、遷移或失敗復原方式時，不得發布。
- 空任務表：HUD 為空狀態，不生成預設小人。
- 混合狀態：每個任務恰好一個小人並進入正確區域。
- 重複 Owner：仍依任務數建立小人。
- 超過 10 個未完成任務：只顯示前 10 個。
- 具有 `Done`：不占未完成額度，超過總上限時淘汰最舊完成項。
- 缺少欄位或格式錯誤：回報明確錯誤且不覆寫既有視覺狀態。

### 發布驗證

- 四份 `SKILL.md` SHA-256 相同。
- repo、個人 Skill 與 Marketplace 的必要檔案清單一致。
- plugin cache 的必要檔案內容與發布來源一致，允許 Codex 自身生成的安裝 metadata。
- Python 腳本編譯與相關測試通過。
- Git diff 僅包含本次 Skill 統合、發布與測試內容。

## 風險控制

- Repo 目前落後 `origin/main` 三個提交，且已有使用者未提交修改；實作不得使用 destructive reset、checkout 或粗暴覆蓋。
- GitHub 版的 active-agent 與 SmokeTest 偽狀態不可直接當成最終規格。
- Cache 版雖具有正確的 task-driven 原則，仍含預設小人與部分語意矛盾，必須依本設計修正後才能成為真源內容。
- 發布流程若不能可靠刷新 cache，應停止並保留已驗證的 repo 與 Marketplace，不宣稱四份已同步。
